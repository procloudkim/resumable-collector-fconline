# 무너지지 않는 수집 파이프라인

몇 년치를 수집해야 하는 크롤링은 한 번에 끝나지 않고 반드시 중간에 끊깁니다. **끊겼을 때 처음부터 다시 하지 않는 것**을 첫 번째 요구사항으로 잡고 만든 로컬 수집 파이프라인입니다.

분석 결론은 "뚜렷한 관계가 없다"였습니다. 남길 만한 것은 그 결론이 아니라 거기까지 가는 과정에서 만든 수집 구조와, **숫자를 세 번 의심한 기록**입니다.

> 개인 프로젝트입니다. 사람 팀원이 없다는 뜻이며 AI 도구, 외부 라이브러리, 공개 데이터를 쓰지 않았다는 뜻은 아닙니다.
>
> **수집한 데이터는 이 저장소에 없습니다.** 코드, 테스트, 거버넌스 문서만 공개합니다. 이유는 아래 [수집 데이터를 왜 뺐나](#수집-데이터를-왜-뺐나)에 있습니다. 원본 비공개 저장소는 그대로 유지되며 링크를 제공하지 않습니다.

## 3분 요약

| 질문 | 답변 |
|---|---|
| 무엇을 만들었나 | 공개 API, 웹 페이지, 댓글 API 세 경로에서 몇 년치 데이터를 모으는, 다시 시작할 수 있는 로컬 파이프라인입니다 |
| 가장 어려웠던 것 | 크롤링이 중간에 끊기는 것이었습니다. 한 번에 끝나지 않는다는 전제에서 설계를 시작해야 했습니다 |
| 어떻게 풀었나 | 결과를 성공, 데이터 없음, 실패 셋으로 나눠 기록하고 진행 상태를 파일로 남깁니다. 저장은 composite key UPSERT라 재실행해도 행이 늘지 않습니다 |
| 무엇이 이 프로젝트의 핵심인가 | 나온 숫자를 세 번 의심하고 그중 둘을 폐기한 것입니다 |
| 폐기한 수치는 | 수집량 168만 건입니다. 실제 레코드는 42만 건대였고, 168만은 줄 수를 잘못 센 값이었습니다 |
| 결과는 | 감성 지표와 출전 합계 사이 선형 관계가 거의 없었습니다. 상관계수는 0.1 미만이었습니다 |
| 그것을 어떻게 썼나 | "약한 양의 상관"이라고 쓰지 않았습니다. **관계가 없다는 것이 결과**입니다 |
| 지금 무엇을 확인할 수 있나 | 코드 160개 파일, 테스트, 거버넌스 문서 7종을 확인할 수 있습니다. 수집 데이터는 없습니다 |
| 무엇을 입증하지 않았나 | 외부 배포, 스케줄러 운영, 테스트 커버리지, 인과관계, 가격 분포는 입증하지 않습니다 |

## 핵심 사례: 숫자를 세 번 의심한 기록

### 1. 수집량이 너무 컸다

수집이 끝나고 파일 줄 수를 세니 168만 건이 나왔습니다. 그런데 실제 레코드 수를 세니 42만 건대였습니다.

원인은 **선수 이름 안에 줄바꿈이 들어 있었기 때문**입니다. 줄 단위로 센 값은 레코드 수가 아니었습니다.

168만은 42만보다 네 배 커 보이는 숫자였지만 폐기했습니다.

### 2. 가격 데이터가 대부분 비어 있었다

가격 컬럼의 유효 비율을 재보니 **8.27퍼센트**였습니다. 90퍼센트 넘게 비어 있다는 뜻입니다. 이 값은 당시 중간 스냅샷 419,940건 기준이며, 아래 최종 분석 레이어 수치와 다른 레이어입니다.

감추지 않고 산출식과 함께 보고했습니다. 가격 기반 분석을 어디까지 할 수 있는지가 여기서 정해지기 때문입니다.

추가로 최고가와 평균가 컬럼의 값이 완전히 같다는 것을 확인했습니다. 파서가 하나의 값을 두 컬럼에 모두 채운 결과였습니다. 따라서 **가격 분포나 변동성은 아예 다룰 수 없습니다**. 그래서 이 저장소는 가격 관련 주장을 하지 않습니다.

### 3. 감성 분석에서 부정이 0.5퍼센트로 나왔다

댓글 감성을 분류했더니 중립 76.6, 긍정 22.8, 부정 0.5퍼센트가 나왔습니다.

여론이 우호적이라고 읽을 수도 있었습니다. 그런데 게임 커뮤니티 댓글에서 부정이 0.5퍼센트일 리가 없습니다. **사전이 부정 표현을 못 잡고 있다는 신호**로 읽었습니다.

그래서 감성을 결론으로 쓰지 않고 탐색 변수로만 썼습니다.

세 경우 모두 도구가 알려준 것이 아닙니다. **나온 숫자가 이상하다고 느껴서 확인한 결과**입니다.

## 만든 구조

```
요청
 │
 ├─ HTTP 우선 시도 ── 실패 ──▶ 재시도 3회 (0.5초 → 1초 → 2초)
 │                                    │
 │                              여전히 빈 응답
 │                                    ▼
 └─────────────────────── 브라우저 자동화로 승급
                                      │
                                      ▼
                          결과 판정: 성공 / 데이터 없음 / 실패
                                      │
        ┌─────────────────────────────┼─────────────────────────┐
        ▼                             ▼                         ▼
   진행 상태 파일               데이터 없는 날 기록          실패한 날 기록
   (다음 실행이 여기서 이어감)                              (별도 파일로 분리)
                                      │
                                      ▼
                          composite key UPSERT로 저장
                          (재실행해도 중복이 쌓이지 않음)
```

**성공과 데이터 없음과 실패를 나눈 것**이 핵심입니다. 셋을 한데 묶으면 재실행할 때 무엇을 다시 해야 할지 알 수 없습니다. 데이터가 원래 없는 날을 계속 재시도하면 시간만 버리고, 실패한 날을 성공으로 처리하면 구멍이 남습니다.

정적 HTTP를 먼저 시도하고 빈 응답일 때만 브라우저 자동화로 올리는 것도 같은 계열의 판단입니다. 브라우저는 느리고 불안정하므로 필요할 때만 씁니다.

중단 후 재개가 실제로 되는지는 테스트로 확인했습니다. 테스트는 `project2/test/test_resume_state.py`에 있습니다.

## 결과

감성 지표와 일별 출전 합계 사이 선형 관계는 거의 없었습니다. 상관계수는 0.1에 못 미쳤습니다.

이걸 "약한 양의 상관이 관찰됐다"고 쓸 수도 있었습니다. 그렇게 쓰지 않았습니다. **관계가 없다는 것이 이번 분석의 결과**입니다.

관계를 찾지 못한 이유도 함께 적었습니다. 두 데이터 소스에 공통 식별자가 없어 정규화한 이름으로 근사 연결했고, 그 과정에서 동명이인과 시즌별 카드를 완전히 구분하지 못합니다. **연결 자체가 느슨하면 관계가 있어도 흐려집니다.**

## 검증된 산출물

최종 분석 레이어 기준입니다. 서로 다른 원천의 행 수를 하나로 합치지 않습니다.

| 항목 | 수치 | 기간 |
|---|---:|---|
| 일별 최고가 레코드 | 25,571 | 2020-05-20 ~ 2025-09-11 |
| 출전 랭킹 레코드 | 71,856 | 2020-05-20 ~ 2025-09-11 |
| 수집 댓글 | 10,495 | 2022-04-02 ~ 2025-09-03 |
| 분석 대상 이벤트 | 13 | 2021-05-22 ~ 2025-05-11 |

폐기한 수치는 위 핵심 사례에 적었습니다. 168만 건은 쓰지 않습니다.

## 수집 데이터를 왜 뺐나

원본 저장소에는 수집 결과가 함께 들어 있습니다. 공개본에서는 전부 뺐습니다.

| 뺀 것 | 이유 |
|---|---|
| 댓글 원문과 작성자 핸들 | 제3자 개인정보입니다. 2.4만 행 규모였습니다 |
| 시세와 출전 raw 데이터 | 대상 서비스의 이용약관 범위를 공개 재배포까지 넓히지 않습니다 |
| SQLite 데이터베이스, 이미지 묶음, 대용량 CSV | 위와 같고, 저장소가 500MB를 넘습니다 |
| 내부 작업 문서 아카이브 | 그중 한 건에 댓글 원문과 작성자 핸들이 표 형태로 들어 있었습니다 |

마지막 항목이 이 작업에서 가장 중요한 발견입니다. **데이터 파일을 전부 제외했는데도 문서 한 건으로 새고 있었습니다.** 데이터 계층만 막으면 놓칩니다.

그래서 `scripts/check_public_tree.py`에 작성자 핸들, 댓글 ID, 댓글 덤프 행 패턴을 규칙으로 넣고 CI가 커밋마다 검사하게 했습니다.

## 수집 전에 먼저 정한 규칙

외부 서비스에서 데이터를 가져오는 프로젝트입니다. 수집을 시작하기 전에 규칙을 문서로 정했습니다.

| 문서 | 정한 것 |
|---|---|
| [CRAWLING_POLICY.md](./docs/CRAWLING_POLICY.md) | 요청 간격, 대상 범위, 하지 않을 것 |
| [PRIVACY.md](./docs/PRIVACY.md) | 개인정보 취급 |
| [DATA_LICENSE.md](./docs/DATA_LICENSE.md) | 출처 표기와 이용 범위 |
| [DATA_STORAGE_POLICY.md](./docs/DATA_STORAGE_POLICY.md) | 무엇을 저장하고 무엇을 Git에 넣지 않을지 |
| [TIMEZONE_POLICY.md](./docs/TIMEZONE_POLICY.md) | 시간대 처리 |
| [ENCODING_POLICY.md](./docs/ENCODING_POLICY.md) | 인코딩 |
| [LOGGING.md](./docs/LOGGING.md) | 로깅 규칙 |

`DATA_STORAGE_POLICY.md`가 "운영 데이터베이스와 이미지는 Git에서 추적하지 않는다"고 정해 둔 것이 이번 공개 작업에서 그대로 기준이 됐습니다. 처음에 정해 둔 규칙이 나중에 판단을 대신해 준 사례입니다.

## 선택과 포기의 이유

| 문제 | 선택 | 포기한 것과 이유 |
|---|---|---|
| 수집이 중간에 끊김 | 진행 상태를 파일로 남기고 이어서 재개 | 매번 처음부터 다시 돌리기를 버렸습니다. 며칠치가 아니라 몇 년치입니다 |
| 재실행 시 중복 | composite key UPSERT | append를 버렸습니다. 다만 CSV append 경로는 이 보호 밖이라 재실행 시 중복이 생길 수 있습니다. 모든 산출물이 idempotent하다고 말하지 않습니다 |
| 크롤링 불안정 | 정적 HTTP 우선, 빈 응답일 때만 브라우저로 승급 | 처음부터 브라우저 쓰기를 버렸습니다. 느리고 불안정합니다 |
| 감성 분류 | seed word 24개 규모의 자체 사전과 규칙 기반 | 학습 모델을 버렸습니다. 5일짜리 프로젝트에 라벨링 비용을 넣을 수 없었습니다. 대신 결과를 결론으로 쓰지 않았습니다 |
| 두 소스에 공통 식별자가 없음 | 정규화한 이름으로 근사 연결 | 완전 연결을 버렸습니다. 그리고 그 한계를 결과 해석에 명시했습니다 |
| 이상한 수치 발견 | 폐기하고 이유를 기록 | 큰 숫자를 쓰기를 버렸습니다 |

## 현재 한계

- **대시보드를 외부에 배포하거나 운영한 적이 없습니다.** 로컬 실행입니다
- **스케줄러를 만들었지만 실제로 돌린 적이 없습니다.** 스크립트가 스스로 일회성 실행이라고 적어 두었습니다
- **테스트 커버리지를 측정한 적이 없습니다.** 테스트 파일과 특정 시점 실행 기록만 있습니다. 커버리지 측정 설정이 저장소에 존재한 적이 없습니다
- 인과관계를 주장하지 않습니다. 대조군도 교란 통제도 없는 탐색적 분석입니다
- 가격 분포와 변동성은 파서 오염 때문에 다룰 수 없습니다
- 수집 데이터가 없으므로 **분석 재현은 이 저장소만으로 불가능합니다.** 코드와 판단 근거를 읽는 용도입니다
- 개인 프로젝트이며 실사용자가 없습니다

## AI 도구를 어떻게 썼나

구현에 코딩 보조 도구를 사용했습니다. 요구사항 정의, 수집 전략 선택, 실패 판정 기준, 어떤 수치를 폐기할지는 제가 판단했습니다.

수집량 168만 건이 오측정이라는 것도, 부정률 0.5퍼센트가 사전 문제라는 것도 도구가 알려준 것이 아닙니다. 나온 숫자가 이상하다고 느껴서 확인한 결과입니다.

## 실행

```bash
pip install -r requirements.txt

pytest                                 # 테스트
python scripts/check_public_tree.py    # 공개 트리 검사
```

실제 수집에는 `NEXON_OPENAPI_API_KEY`와 `YOUTUBE_API_KEY`가 필요합니다. 설정 예시는 `config/*.sample.*`에 있고 실제 설정 파일은 저장소에 없습니다.

수집 데이터가 없으므로 대시보드는 빈 화면으로 뜹니다. 코드와 문서를 읽는 것이 이 저장소의 용도입니다.
